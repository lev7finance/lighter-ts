# 05 — REST API Surface & Data Models

**Status:** functional specification (clean-room). Describes *what the Lighter REST API is*, not how any
reference SDK implements it.
**Scope:** HTTP transport, endpoint contracts, auth, envelope/error semantics, response models, and the
TypeScript design that should replace the generated Python/Go clients.
**Sibling specs:** crypto/signer (auth-token signature construction), tx codec (`tx_info` payloads),
WebSocket (`/stream`).

---

## 0. How this document was derived, and its authority

Three independent sources were reconciled:

| Source | What it gave | Trust level |
|---|---|---|
| `openapi.json` in the Python SDK repo (OpenAPI 3.0.0, 78 paths, 142 schemas, generator v7.7.0) | The complete path/param/response index | **Authoritative for paths, params, enums, defaults, limits.** Stale for response field sets. |
| `docs/*.md` + `lighter/api/*.py` (generated from the same document) | Cross-check: 78 operations across 13 groups — exact match, no drift | Confirmatory only |
| **Live probes against `https://mainnet.zklighter.elliot.ai`** | Actual response bodies, actual error codes, actual auth enforcement, actual HTTP statuses | **Authoritative for response shapes, error taxonomy, and runtime nullability.** |

The live probing was essential: **the checked-in OpenAPI document is materially wrong about response
shapes** in ways that would produce an unsound TypeScript type layer if trusted blindly. Section 9
enumerates the drift. This is the single most important input to the design decision in Section 11.

## 1. Hosts and endpoint profiles

There is no path-based or header-based environment switch — each environment is a distinct origin. The
REST base and the WebSocket base always share a host.

| Profile | REST base | WebSocket | L2 chain id |
|---|---|---|---|
| `mainnet` (default) | `https://mainnet.zklighter.elliot.ai` | `wss://mainnet.zklighter.elliot.ai/stream` | `304` |
| `testnet` | `https://testnet.zklighter.elliot.ai` | `wss://testnet.zklighter.elliot.ai/stream` | `300` |
| `robinhood` | `https://api.rh.lighter.xyz` | `wss://api.rh.lighter.xyz/stream` | `466324` |
| `robinhood_testnet` | `https://api.rh-testnet.lighter.xyz` | `wss://api.rh-testnet.lighter.xyz/stream` | `300` |

Notes that matter:

- The chain id is **not** a REST concern — it is a signing-domain parameter that must be bound to the
  same profile object, because signing a transaction for chain 304 and posting it to testnet is a silent
  failure mode. Keep `chainId` on the profile so it is impossible to mismatch.
- **`robinhood_testnet` and `testnet` share chain id `300`.** Signatures are therefore cross-valid between
  those two environments. This is a property of the upstream system, not a bug to fix, but it is worth a
  comment in the code so nobody "corrects" it.
- All API v1 paths are prefixed `/api/v1`. Exactly two operations sit at the origin root: `GET /` and
  `GET /info`. Do **not** bake `/api/v1` into the base URL — the base URL is the origin, and each route
  carries its own full path.
- Base URLs must be normalised by stripping trailing slashes before joining, so that a user-supplied
  `https://host/` and `https://host` behave identically.

### 1.1 Browser / Worker viability (verified)

Every response carries:

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
Access-Control-Allow-Headers: Content-Type, Origin, X-CSRF-Token, Authorization, AccessToken, Token, Range
Access-Control-Allow-Methods: GET, HEAD, POST, PATCH, PUT, DELETE
Access-Control-Max-Age: 86400
```

`Authorization` is on the allow-list, so the auth scheme works from a browser with no proxy. This
validates the "runs unmodified in browsers and Cloudflare Workers" constraint for the REST layer. No
custom headers beyond `Authorization` and `Content-Type` may be sent, or the preflight will fail —
in particular **do not add a `User-Agent` or `X-Client-Version` header**; they are not in the allow-list
and browsers forbid setting `User-Agent` anyway.

### 1.2 CDN interposition (important, undocumented)

The origin sits behind CloudFront. Certain requests are answered by the CDN/WAF, not the API, with an
**HTML** body and `HTTP 403`:

```
HTTP/1.1 403 Forbidden
Content-Type: text/html
<!DOCTYPE HTML ...><H1>403 ERROR</H1><H2>The request could not be satisfied.</H2>
... Generated by cloudfront (CloudFront) Request ID: <id>
```

Observed on `/api/v1/blocks`, `/api/v1/currentHeight`, `/api/v1/accountTxs`, and unknown paths, from a
datacenter IP. It is **not** correlated with the endpoint being invalid — the same paths are documented,
generated, and presumably work from residential/allow-listed IPs. The classifier appears to be
IP-reputation based.

**Requirement:** the transport must never assume a non-2xx body is JSON. Parsing must be attempted and
failure must degrade to a typed error carrying the raw text and the response status, not throw a
`SyntaxError` from `JSON.parse`. This is a real, reproducible failure mode, not defensive paranoia.

## 2. Wire conventions

### 2.1 Casing and content types

- Every JSON key on both request and response is **`snake_case`**. There are no exceptions, including
  the single-letter candle keys (Section 10.6).
- Responses: `application/json; charset=utf-8`.
- Requests:
  - `GET` — all input in the query string.
  - `POST` — **`application/x-www-form-urlencoded`** for every operation except one.
  - The sole exception is `POST /api/v1/setAccountMetadata`, which takes **`application/json`**.
  - `POST /api/v1/setMakerOnlyApiKeys` additionally advertises `multipart/form-data`; there is no reason
    to use it, and multipart should not be implemented.

  This "forms everywhere except one JSON endpoint" split is accidental complexity inherited from the
  server's handler framework. The TS client should hide it: the route definition declares its body
  encoding, and the transport serialises accordingly. Callers always pass a plain object.

### 2.2 Query string serialisation

- Booleans serialise as the lowercase literals `true` / `false`.
- Numbers serialise as decimal, no thousands separators, no exponent.
- Absent/undefined params must be **omitted entirely**, not sent as empty. Several endpoints treat an
  empty string differently from an absent key.
- **Array params repeat the key** (OpenAPI `style=form, explode=true`, i.e. the generator's `multi`
  collection format). There are exactly two:
  - `GET /api/v1/accountTxs` → `types` (array of `u8`) → `?types=14&types=15`
  - `GET /api/v1/transfer/history` → `type` (array of enum) → `?type=L2Transfer&type=L2MintShares`

  Every other array-shaped input is passed as a **JSON-encoded string inside a single field**, not as a
  repeated param. See §2.3.
- Percent-encoding: standard `application/x-www-form-urlencoded` rules. `URLSearchParams` produces the
  correct output, including encoding `:` inside the `auth` query param, which the server accepts.

### 2.3 JSON-in-a-string fields

Several fields carry structured data as an opaque JSON string rather than as a native type. These are
protocol requirements and must be reproduced exactly:

| Operation | Field | Content |
|---|---|---|
| `POST /api/v1/sendTx` | `tx_info` | JSON object (the signed transaction). Must begin with `{`. |
| `POST /api/v1/sendTxBatch` | `tx_types` | JSON array of integers, e.g. `[14,15]` |
| `POST /api/v1/sendTxBatch` | `tx_infos` | JSON array of **strings**, each itself a JSON object |
| `POST /api/v1/setMakerOnlyApiKeys` | `api_key_indexes` | JSON array of integers, e.g. `[4,5]`; `[]` clears |
| `POST /api/v1/litLease` | `tx_info` | JSON object (signed transfer) |
| `POST /api/v1/fastwithdraw` | `tx_info` | JSON object (signed withdraw) |
| `POST /api/v1/setAccountMetadata` | `metadata` | JSON string field inside a JSON body |
| responses `Tx.info`, `Tx.event_info` | | JSON strings; parse lazily, never eagerly |

`sendTxBatch` requires `tx_types.length === tx_infos.length` and a non-empty batch; the server's error for
a mismatch is unhelpful, so the client should validate locally before the round-trip.

### 2.4 Numeric domains — the `_str` convention and the 2^53 problem

The server is Go. Integers are emitted as JSON numbers with full `int64` range. JavaScript's `JSON.parse`
silently loses precision above 2^53−1. This is a correctness landmine, and the API partially anticipates it.

Observed live: order ids around `5.6e14`, trade ids around `2.6e10`, `transaction_time` around `1.78e15`,
and `insurance_fund_account_index = 281474976710655` (= 2^48−1, the sentinel for "none"). All are currently
below 2^53, but order-id and trade-id sequences are monotonic and unbounded.

**The API's own mitigation:** identity fields are duplicated as decimal strings with a `_str` suffix.
Confirmed present in live `Trade` objects:

`trade_id` / `trade_id_str`, `ask_id` / `ask_id_str`, `bid_id` / `bid_id_str`,
`ask_client_id` / `ask_client_id_str`, `bid_client_id` / `bid_client_id_str`.

`Order` follows the same pattern with `order_index` (number) alongside `order_id` (string), and
`client_order_index` alongside `client_order_id`.

**Rules for the TS SDK:**

1. Where a `_str` variant exists, **the string variant is canonical**. Type the numeric twin as
   `number` but mark it deprecated in the doc comment and never use it in SDK-internal logic.
2. Where no `_str` variant exists and the field is `int64`-domain (`sequence_index`, `block_height`,
   `nonce`, `transaction_time`, `expire_at`, `order_expiry`, `*_timestamp`, `account_index`), expose
   `number`. These are either bounded by real-world magnitude (timestamps, heights) or by protocol
   (`account_index` is capped at 2^48−1 by the sentinel convention).
3. **Do not ship a BigInt-aware JSON reviver by default.** It would force `bigint` into every model,
   is a large hidden cost on hot paths (order book snapshots), and solves a problem the `_str` fields
   already solve. Offer it as an opt-in transport hook for users who need `sequence_index` exactness.
4. **All monetary and size quantities are strings, not numbers** — `collateral`, `available_balance`,
   `price`, `size`, `initial_base_amount`, `remaining_base_amount`, `position`, `unrealized_pnl`,
   `taker_fee`, `min_base_amount`, etc. They are fixed-point decimals rendered at the market's declared
   precision (`"64397.7"`, `"0.00089"`, `"3113.800050"`). **Never** parse these to `number` inside the
   SDK. Expose them as `string` and provide explicit fixed-point helpers.
5. Statistical/derived fields *are* floats: `last_trade_price`, `daily_price_change`, `open_interest`,
   `annual_percentage_yield`, `avg_slippage`, `sharpe_ratio`, and all candle OHLCV values. This
   string/number split is inconsistent but is a wire fact.
6. **Timestamp units are not uniform.** Most are epoch **milliseconds** (`timestamp`, `order_expiry`,
   `created_at` on orders/trades, and the `start_timestamp`/`end_timestamp` inputs to `candles`,
   `fundings`, `pnl`, `export`). But `transaction_time` is **microseconds** (`1785022751987984`), the root
   `GET /` `timestamp` is **seconds** (`1785022683`), `Announcement.created_at`/`expired_at` are
   **seconds**, and `ExecuteStat.timestamp` is **seconds**. The auth-token deadline is **seconds**. There
   is no marker in the payload distinguishing them. The SDK must document the unit per field and must not
   apply a blanket `new Date(x)`.

### 2.5 Vestigial `code` / `message` on nested objects

The server's Go structs embed a shared result-code struct, and that embedding leaks into nested models.
Live example from `accountsByL1Address`:

```
{"code":200,"l1_address":"0x…","sub_accounts":[{"code":0,"account_type":0,"index":0, …}]}
```

Each `Account` inside `sub_accounts` carries `"code": 0`. Same for `DetailedAccount` inside
`DetailedAccounts.accounts`. These nested `code`/`message` fields are **meaningless** — always `0`/absent —
and must not be surfaced as part of the SDK's public model types. Strip them from the hand-authored core
types; if generated types are used, `Omit<>` them.

## 3. Response envelope

### 3.1 The convention

Success and failure are distinguished **twice, redundantly**: by HTTP status and by an in-body `code`.

**Success:** HTTP `200`, body is the operation's response model, which *includes* a top-level
`code: 200` field alongside the payload:

```
{"code":200,"order_books":[{"symbol":"BTC","market_id":1, …}]}
{"code":200,"nonce":1}
```

**Failure:** HTTP `400` (or `401`), body is `ResultCode`:

```
{"code":21602,"message":"invalid market index"}
```

`ResultCode` is the universal error model and also the structural base of nearly every success model:

```
ResultCode = { code: int32; message?: string }
```

`message` is `omitempty` — it is **absent**, not `null`, on success.

### 3.2 The three endpoints that break the envelope

Verified live. These return `200` with **no `code` field at all**:

| Operation | Body |
|---|---|
| `GET /api/v1/withdrawalDelay` | `{"seconds":1072}` |
| `GET /api/v1/executeStats` | `{"period":"d","result":[…]}` |
| `GET /api/v1/referral/points` | `{"referrals":[…],"user_total_points":…, …}` (auth-gated; per schema) |

A success check written as `body.code === 200` therefore **fails on these three**. The correct predicate is:

> The request succeeded iff the HTTP status is 2xx **and** (`code` is absent **or** `code === 200`).

HTTP status is the primary signal; `code` is a secondary, non-universal one. Any implementation that
inverts that priority (as the reference Go client does — it parses `code` first and only then checks the
status) will misclassify these three endpoints. Do not replicate that.

### 3.3 Meaning of `code`

- `200` — success sentinel. Not an HTTP status; it just happens to share the value.
- Any other value — a domain error code (Section 4). Non-200 `code` values only ever appear with a
  non-2xx HTTP status in observation, so the two signals agree in practice; the client should trust HTTP
  status and use `code` for typed discrimination.
- `0` — only on vestigial nested structs (§2.5). Never meaningful.

## 4. Error taxonomy

### 4.1 HTTP status layer

| Status | Meaning | Body |
|---|---|---|
| `200` | Success | Response model |
| `400` | Validation failure, or domain "not found" | `ResultCode` JSON |
| `401` | Auth token invalid, expired, or malformed | `ResultCode` JSON |
| `403` | **CDN/WAF rejection** — not from the API | HTML |
| `5xx` | Upstream/origin failure | Unspecified; may be HTML |

Note the unusual choice: **"not found" is `400`, not `404`.** `GET /api/v1/account?by=index&value=999999999`
returns `HTTP 400 {"code":29404,"message":"not found"}`. A client that maps 404→`NotFoundError` will never
fire; the not-found signal lives entirely in `code`.

### 4.2 Domain codes (observed live, mainnet)

| `code` | HTTP | `message` | Trigger |
|---|---|---|---|
| `200` | 200 | — | success |
| `20001` | 400 | `invalid param ` (note trailing space) | missing required param, bad enum, out-of-range `limit`, unknown symbol |
| `20001` | 400 | `invalid param : auth query param and Authorization header are empty` | auth absent |
| `20001` | 400 | `invalid param : Authorization header is empty` | auth absent, header-only endpoint |
| `20001` | 400 | `invalid param : auth required for main accounts` | auth absent for a master account |
| `20001` | 400 | `invalid param : unknown market: <sym>` | bad `symbol` |
| `20001` | 400 | `invalid param : invalid period for the requested metric kind` | bad `period`/`kind` combination |
| `20013` | **401** | `invalid auth: invalid auth string` | token not parseable |
| `20013` | **401** | `invalid auth: expired token` | deadline in the past |
| `20013` | **401** | `invalid auth: invalid deadline` | deadline > 8h in the future, **or** signature invalid |
| `20558` | 400 | `You are accessing Lighter from a restricted jurisdiction…` | geo-block, on write paths |
| `21100` | 400 | `account not found` | unknown account on transfer history |
| `21500` | 400 | `transaction not found` | unknown tx hash / sequence index / L1 hash |
| `21602` | 400 | `invalid market index` | `market_id` out of range |
| `22403` | 400 | `time range exceeds maximum allowed range for the specified resolution` | over-wide candle/pnl window |
| `29404` | 400 | `not found` | generic entity miss |

Structure of the numbering (inferred, treat as a hint not a contract):
`20xxx` = request/auth validation · `21xxx` = entity lookup, per-domain (`211xx` account, `215xx` tx,
`216xx` market) · `22xxx` = query/range constraints · `29xxx` = generic.

**The code list is open.** Neither reference SDK enumerates it, and no published registry exists. The SDK
must therefore **not** model codes as a closed TypeScript union — that would break the moment the server
adds a code. Model as `number` with a set of exported named constants for the known values.

Also note `20013` is deliberately ambiguous between "bad deadline" and "bad signature" — the server does
not distinguish them, presumably to avoid a signature oracle. Do not attempt to infer which; surface the
message verbatim.

### 4.3 Error class hierarchy (recommended)

Reference SDKs expose OpenAPI-generator boilerplate (`ApiTypeError`, `ApiValueError`, `ApiAttributeError`,
`ApiKeyError`, plus status-keyed `BadRequestException` / `UnauthorizedException` / `ForbiddenException` /
`NotFoundException` / `ServiceException`). Most of that is dead weight — `NotFoundException` can never fire
because not-found is a 400, and the `ApiTypeError` family is an artifact of Python's dynamic deserialisation
with no TypeScript analogue.

Ship exactly this instead:

```
LighterError                    (base; extends Error)
├─ LighterApiError              HTTP reached the API and it returned a structured refusal
│   .status: number             HTTP status
│   .code: number               domain code from the body
│   .messageText: string        server `message`, verbatim
│   .path: string               request path (no query, no secrets)
│   .requestId?: string         x-amz-cf-id when present, for support tickets
│   .body: unknown              parsed body
├─ LighterAuthError             extends LighterApiError; status 401 or code 20013
│   .reason: 'malformed' | 'expired' | 'deadline-or-signature'
├─ LighterBlockedError          extends LighterError; HTTP 403 with non-JSON body (CDN/WAF)
│   .rawBody: string
├─ LighterTransportError        fetch rejected: DNS, TLS, connection reset, abort
│   .cause: unknown
└─ LighterTimeoutError          extends LighterTransportError; our AbortSignal fired
```

Every error carries `.path` and `.requestId`. Do **not** put the query string on the error — the `auth`
query param is a bearer credential and would end up in logs.

Provide a type guard `isLighterApiError(e)` and a `hasCode(e, code)` helper; users should never have to
`instanceof` across a bundler boundary.

## 5. Authentication

There are **two independent credential systems**. They are unrelated and easily confused.

### 5.1 The declared-but-unused OpenAPI security scheme

`openapi.json` declares:

```
securitySchemes.apiKey = { type: apiKey, in: header, name: Authorization,
                           description: "Enter JWT Bearer token only" }
```

**This is dead metadata.** Verified: zero of the 78 operations reference it (no per-operation `security`,
no global `security`), and the token is **not** a JWT and takes **no `Bearer ` prefix**. Live confirmation:
sending `Authorization: <deadline>:<acct>:<key>:<sig>` with no prefix is parsed by the server (it returns
`expired token`, i.e. it got past parsing). Ignore the declaration entirely; it will mislead any
code generator pointed at this document.

### 5.2 Scheme A — signed auth token (the primary scheme)

A short-lived, self-contained bearer credential produced by signing with an account's API key. This is
what the read-only-auth flow and all authed reads use.

**Format** — four colon-separated ASCII fields, no whitespace, no prefix:

```
<deadline>:<account_index>:<api_key_index>:<signature_hex>
```

- `deadline` — Unix epoch **seconds**, decimal.
- `account_index` — decimal `int64`.
- `api_key_index` — decimal `uint8`, `0..253`.
- `signature_hex` — lowercase hex, **no `0x` prefix**.

**Construction** (full detail belongs to the crypto spec; stated here so the REST layer's contract is
self-contained):

1. Build the ASCII message `M = "<deadline>:<account_index>:<api_key_index>"` — i.e. the token minus the
   signature field. The signed message is exactly the token's own prefix.
2. Interpret `M`'s bytes as Goldilocks field elements via the canonical little-endian byte→field-array
   encoding.
3. Hash with Poseidon2 into the quintic extension field; serialise the 5-element result to little-endian
   bytes (40 bytes).
4. Schnorr-sign those bytes with the API key's private key, using Poseidon2 as the transcript hash.
5. Hex-encode the signature, lowercase, unprefixed.
6. Token = `M + ":" + signature_hex`.

**Transmission** — two interchangeable channels:

- **Header:** `Authorization: <token>` (no scheme prefix). Preferred.
- **Query param:** `?auth=<token>`.
- **Form field:** `auth=<token>` in the POST body, for the form-encoded write endpoints.

The OpenAPI document declares `auth` as an accepted query param on only four operations (`leases`,
`referral/userReferrals`, `referral/get`, `accountTxs`). **This is wrong.** Verified live: `auth` as a
query param is accepted on `accountActiveOrders`, which does not declare it. The server checks both
channels uniformly — the error text `"auth query param and Authorization header are empty"` on endpoints
that declare neither confirms a single shared code path. Treat header and query as universally
interchangeable; prefer the header.

`GET /api/v1/referral/get` declares `authorization` as a **query** parameter rather than a header. That is
a spec bug of the same family; send the header.

**Expiry policy** (verified by probe):

- Maximum lifetime is **8 hours**. A deadline more than 8h in the future is rejected with
  `invalid auth: invalid deadline` — the server bounds the forward window, it does not merely check
  `now < deadline`.
- A past deadline gives `invalid auth: expired token`.
- The reference default is 10 minutes.
- The pre-generation pattern documented upstream: generate tokens on **6-hour-aligned** boundaries
  (`floor(t / 21600) * 21600`) each valid for **8 hours**, giving 2 hours of overlap so a lookup by
  current aligned bucket always yields a live token. This exists so a long-running read-only service can
  hold pre-minted tokens and never hold the private key.
- Convention: dedicate **API key index 253** to read-only token minting. It is the top of the valid range
  `0..253` and is not used for trading, so rotating it (via a change-pubkey transaction) invalidates every
  outstanding read-only token at once without disturbing trading keys.

**SDK requirement:** the client must accept an auth *provider*, not an auth *string*:

```
type AuthProvider = (ctx: { accountIndex: number }) => string | Promise<string>
```

so that a caller can plug in (a) a signer that mints on demand with caching, (b) a static pre-generated
token, or (c) a lookup table keyed by 6-hour bucket. A raw string must still be accepted and wrapped.
Tokens must be minted lazily, cached until `deadline - skew` (skew ≈ 60s), and re-minted on `20013`
exactly once before the error propagates — a clock-skew retry, not a general retry.

### 5.3 Scheme B — managed API tokens (read-only, server-stored)

A separate, longer-lived credential the server issues and stores, so a third party can be granted scoped
read access without ever seeing a private key.

| Operation | Purpose |
|---|---|
| `POST /api/v1/tokens/create` | mint; body `name`, `account_index`, `expiry`, `sub_account_access`, `scopes` (default `read.*`) |
| `GET /api/v1/tokens` | list tokens for an account |
| `POST /api/v1/tokens/revoke` | revoke by `token_id` |

Returns `RespPostApiToken { token_id, api_token, name, account_index, expiry, sub_account_access, revoked, scopes }`.
The `api_token` string is the credential. `scopes` is a free-form string (observed default `read.*`), not
an enum. All three management operations are themselves authenticated with **Scheme A**.

Where the resulting `api_token` is presented is **not** stated by either reference SDK, the OpenAPI
document, or any example — nothing in the reference material consumes it. Almost certainly the same
`Authorization` header, since the server's auth entry point is shared, but **this is unverified**. See
Open Questions.

### 5.4 Auth requirement per operation

Derived from the OpenAPI `authorization` header parameter, then corrected against live probes.

**`authorization` declared REQUIRED (19 operations)** — `accountLimits`, `getMakerOnlyApiKeys`,
`l1Metadata`, `liquidations`, `setMakerOnlyApiKeys`, `rfq/create`, `rfq/get`, `rfq/list`, `rfq/respond`,
`rfq/update`, `fastwithdraw/info`, `transferFeeInfo`, `accountActiveOrders`, `accountInactiveOrders`,
`export`, `referral/points`, `deposit/history`, `withdraw/history`.

**Declared optional but *enforced* at runtime (verified 400 without auth):** `accountMetadata`,
`positionFunding` (message: `auth required for main accounts`), `leases`, `tokens`, `referral/get`,
`trades`. `trades` is the notable one — the OpenAPI marks `authorization` optional and the endpoint has no
required account parameter, yet an unauthenticated call returns
`{"code":20001,"message":"invalid param : auth query param and Authorization header are empty"}`.
**Treat `trades` as requiring auth.**

**Declared optional and genuinely optional (verified 200 without auth):** `publicPoolsMetadata` (auth only
needed when filtering by `account_index`), `pnl` (rejected on range, not auth), `transfer/history`
(rejected on account lookup, not auth — public pools are readable unauthenticated).

**Genuinely public (no auth parameter):** `account`, `accountsByL1Address`, `apikeys`, `leaseOptions`,
`partnerStats`, `announcement`, `block`, `blocks`, `currentHeight`, `createIntentAddress`,
`deposit/latest`, `deposit/networks`, `fastbridge/info`, `candles`, `fundings`, `funding-rates`,
`layer1BasicInfo`, `syntheticSpotInfo`, `systemConfig`, `withdrawalDelay`, `assetDetails`,
`exchangeMetrics`, `exchangeStats`, `executeStats`, `orderBookDetails`, `orderBookOrders`, `orderBooks`,
`recentTrades`, `tokenlist`, `blockTxs`, `nextNonce`, `tx`, `txFromL1TxHash`, `txs`, `GET /`, `GET /info`.

**`sendTx` and `sendTxBatch` take no auth token** — authentication is the signature inside `tx_info`
itself. This is important: the write path and the read path use the same key material but entirely
different mechanisms.

**Design consequence:** because runtime enforcement diverges from the document, auth requirement must be a
**hand-maintained field on each route definition**, seeded from the OpenAPI doc and corrected by the live
findings above. It must never be re-derived from the OpenAPI document by a generator.

## 6. Pagination

Cursor-based, opaque, forward-only. There is no offset/page/total-pages mechanism. Some collection
endpoints are not paginated at all (`orderBookOrders`, `recentTrades`, `orderBooks` — these take a bare
`limit`).

**The cursor field name is inconsistent** — a wart that must be normalised:

| Field | Response models |
|---|---|
| `next_cursor` | `DetailedAccounts`, `AccountMetadatas`, `SubAccounts`, `Orders`, `Trades`, `PositionFundings`, `LiquidationInfos`, `RespGetLeases`, `RespListRFQs` |
| `cursor` | `DepositHistory`, `WithdrawHistory`, `TransferHistory`, `UserReferrals` |

The request parameter is always `cursor`.

Semantics:
- Pass the previous response's cursor value back as `?cursor=…` for the next page.
- **Exhaustion is signalled by the field being absent** (`omitempty`), not by an empty string and not by
  `null`. Verified: a single-page `account` response contains no `next_cursor` key at all.
- Never construct or parse a cursor. It is opaque.
- `limit` bounds differ per endpoint and are enforced server-side with a bare `invalid param` on
  violation: `1..100` for most, `1..250` for `orderBookOrders`, `1..300` for `referral/userReferrals`,
  default `20` for `leases` and `rfq/list`.

**SDK requirement:** one normaliser reads either field name, and one async-iterator helper drives it:

```
for await (const page of client.paginate(client.order.accountInactiveOrders, { accountIndex, limit: 100 }))
```

yielding pages (not items) so callers control concurrency and can stop early. It must also expose an
items-flattening variant. Guard against a server returning the same cursor twice — bound the loop and
throw rather than spin forever.

## 7. Timeouts, retries, rate limits

### 7.1 What the reference clients do

The Python client wraps `aiohttp` with a default timeout of **300 seconds** and, when `retries` is
configured, an exponential-retry wrapper restricted to **idempotent methods only**
(`GET, HEAD, PUT, DELETE, OPTIONS, TRACE` — notably *not* `POST`). Its retry parameters are degenerate:
`factor=0.0, start_timeout=0.0, max_timeout=120.0`, which is a **tight spin with no backoff**. Retries are
`None` by default, so this is off unless explicitly enabled. The Go client uses a 30s total timeout, 10s
dial, 60s keep-alive, TLS 1.2 floor, 1000 max conns/host, 100 idle/host.

**Do not copy the Python retry configuration.** A zero-factor exponential retry is a bug — under an origin
brownout it becomes a hot loop against the server. The 300s default timeout is also far too long for a
trading client; a stuck order-book fetch should fail in seconds.

### 7.2 What to do instead

- **Default timeout: 10 s** for reads, **30 s** for `sendTx`/`sendTxBatch`. Per-request override.
  Implemented with `AbortSignal.timeout(ms)`, composed with any caller-supplied signal via
  `AbortSignal.any([...])` — both are available on all five target runtimes.
- **Retry only idempotent GETs**, and only on: transport failure, HTTP `429`, HTTP `5xx`. Never retry a
  `4xx` other than `429`. **Never retry `POST`** — `sendTx` is nonce-bound and a duplicate submission is a
  real economic risk.
- **Backoff:** full-jittered exponential, base 200 ms, factor 2, cap 5 s, default **2** retries. Honour
  `Retry-After` if present.
- The single exception to "never retry on 4xx": a `20013` auth failure triggers **one** token re-mint and
  replay, because the likeliest cause is clock skew or a token that expired mid-flight. Bounded at one.
- Concurrency limiting is the caller's job. Do not build a queue into the client; expose the `fetch`
  override so users can wrap it.

### 7.3 Rate limits

**No rate limiting is discoverable from the client side.** 30 rapid sequential requests to
`/api/v1/orderBooks` all returned `200`. No `X-RateLimit-*`, no `RateLimit-*`, no `Retry-After` on any
observed response. Neither reference SDK contains any 429 handling, backoff-on-429 logic, or rate-limit
header parsing.

Limits certainly exist server-side (unpublished, likely per-IP at the CDN and per-account at the origin).
The 403-with-HTML behaviour in §1.2 may be the CDN's expression of exactly that. Build the `429` path
anyway — it costs nothing and the absence of a limit today is not a contract.

### 7.4 What `endpoint_profiles` encodes

Only the four-field profile record described in Section 1: `name`, `api_url`, `ws_url`, `chain_id`, plus
URL normalisation (trailing-slash strip) and a name→profile registry with a constructor for custom
deployments. It carries **no** retry, timeout, or rate-limit policy. It is the right shape and should be
kept; the TS version should add `restBase`/`wsBase` naming and freeze the objects.

## 9. OpenAPI drift — measured, and why it decides the design

The checked-in `openapi.json` was diffed field-by-field against live mainnet responses. Two categories of
error were found, and the second one is fatal to a naive generate-from-spec approach.

### 9.1 Fields the server sends that the document omits

| Model | Extra fields observed live |
|---|---|
| `PerpsOrderBookDetail` | `created_at` (string!), `multiplier` (string), `mark_price` (string), `index_price` (string), `market_flags` (int), `funding_premium_multiplier` (int) |
| `OrderBook` | `created_at` (string), `multiplier` (string) |
| `Asset` | `multiplier` (string) |
| `DetailedAccount` | `metadata` |

`mark_price` and `index_price` are missing from the document and are **essential for trading** — they are
the basis of liquidation and funding. A generated client that trusts the document would not expose them.

### 9.2 Fields the document marks *required* that the server omits (the fatal one)

The server is Go with `omitempty` on most struct fields, so **any zero-valued field is absent from the
JSON**. The OpenAPI document nonetheless marks ~95% of response fields `required`.

Measured on a live `Trade` object — these are all `required: true` in the document and all **absent**
from the wire:

`taker_fee`, `ask_account_pnl`, `bid_account_pnl`, `maker_position_sign_changed`,
`taker_position_sign_changed`, `integrator_maker_fee`, `integrator_taker_fee`,
`integrator_maker_fee_collector_index`, `integrator_taker_fee_collector_index`,
`taker_allocated_margin_usdc_before`, `taker_allocated_margin_usdc_after`,
`maker_allocated_margin_usdc_before`, `maker_allocated_margin_usdc_after`.

Also measured absent-when-zero: `Candle.C/H/L/O`, `DetailedAccount.pool_info`,
`DetailedAccount.approved_integrators`, `Trades.next_cursor`, `message` on every success envelope.

**Implication.** Generating types with `required` honoured produces a type layer that lies:
`trade.taker_fee` types as `number` and is `undefined` at runtime. With `strictNullChecks` this is
precisely the class of bug the type system exists to prevent, and it would ship silently.

There are only two sound responses: (a) generate and then force every response field optional, or
(b) hand-author the types that matter with correct optionality. Section 11 chooses.

### 9.3 Other document defects

- `securitySchemes.apiKey` declared and referenced by nothing (§5.1).
- `authorization` declared as a **query** param on `referral/get` where every sibling declares a header.
- `auth` query param under-declared — accepted on all authed endpoints, documented on four (§5.2).
- `trades` marked auth-optional; enforced at runtime (§5.4).
- Typo in the document's own format strings: `"format": "uin16"` (missing `t`) on
  `Block.size`, `PerpsOrderBookDetail.default_initial_margin_fraction` / `min_initial_margin_fraction` /
  `maintenance_margin_fraction` / `closeout_margin_fraction`, and `Trade.*_initial_margin_fraction_before`.
  A strict generator will either fail or emit `any`.
- `info.title` and `info.version` are empty strings — the document is unversioned, so there is no way to
  detect that it has changed other than by hashing it.
- `OrderBookDepth` and `PriceLevel` exist in the SDK's `docs/` and model directories but **not** in
  `openapi.json`. They are hand-added WebSocket payload types (`{code, message?, asks: PriceLevel[],
  bids: PriceLevel[], offset, nonce}` and `{price: string, size: string}`). They belong to the WS spec,
  not this one, but a REST-only generator will not produce them.

| **P. Misc** | ~5 | `Announcement`, `Token`, `TokenList`, `ApprovedIntegrator`, `MarketConfig` | Generate, except `MarketConfig` (hand — trading-relevant). |

Roughly **40 hand-authored**, **~100 generated**, matching the brief's split.

### 10.2 Universal conventions for the core models

- The envelope base `ResultCode { code: number; message?: string }` is mixed into every top-level
  response except the three in §3.2.
- **On response models, every field is optional** except `code`. This is not defensive style; it is what
  the wire does (§9.2).
- Nested `code`/`message` (§2.5) are stripped from public types.
- Money/size/price: `string`. Statistical: `number`. Ids: prefer `*_str`.

### 10.3 Markets — `OrderBook`, `PerpsOrderBookDetail`, `SpotOrderBookDetail`

`OrderBook` (from `GET /api/v1/orderBooks`) is the minimal market descriptor. Fields, with live-verified
additions marked `[+]`:

```
symbol                    string     "BTC"
market_id                 i16        the market index used in every other call and in tx signing
market_type               'perp' | 'spot'
base_asset_id             i16
quote_asset_id            i16
status                    'active' | 'inactive'
taker_fee                 string     percent, e.g. "0.0000"
maker_fee                 string     percent
is_taker_fee_enabled      bool
is_maker_fee_enabled      bool
liquidation_fee           string     percent, e.g. "1.0000"
min_base_amount           string     "0.00020"
min_quote_amount          string     "10.000000"
order_quote_limit         string     "281474976.710655"  (= (2^48-1)/1e6)
supported_size_decimals   u8         5
supported_price_decimals  u8         1
supported_quote_decimals  u8         6
created_at            [+] string     epoch ms as a STRING — "1737098461107"
multiplier            [+] string     "1.000000000000000000"
```

`supported_size_decimals` and `supported_price_decimals` are **the scaling factors for order
submission**: an order's integer `base_amount` is `size × 10^supported_size_decimals` and its integer
`price` is `price × 10^supported_price_decimals`. Every order-placement helper depends on these, so
`orderBooks`/`orderBookDetails` must be fetched and cached before trading. This coupling to the tx codec
must be explicit in the API.

`PerpsOrderBookDetail` (from `GET /api/v1/orderBookDetails`) = all of `OrderBook` plus:

```

price_decimals                    u8    duplicate of supported_price_decimals
quote_multiplier                  i64
default_initial_margin_fraction   u16   500  → basis points; 500 = 5% = 20x
min_initial_margin_fraction       u16   200  → 2% = 50x max leverage
maintenance_margin_fraction       u16   120
closeout_margin_fraction          u16   80
mark_price                    [+] string  "64398.5"  — liquidation basis
index_price                   [+] string  "64422.5"  — oracle
last_trade_price                  f64    64398.7     (number, not string)
daily_trades_count                i64
daily_base_token_volume           f64
daily_quote_token_volume          f64
daily_price_low                   f64
daily_price_high                  f64
daily_price_change                f64   percent
open_interest                     f64
daily_chart                       Record<string, f64>   often {} — do not assume populated
market_config                     MarketConfig
strategy_index                    u8
market_flags                  [+] i32   bitfield, semantics unknown
funding_premium_multiplier    [+] i32   100
funding_clamp_small               string "0.0500"
funding_clamp_big                 string "4.0000"
base_interest_rate                string "0.0100"
```

Margin fractions are **basis points**: `leverage = 10000 / initial_margin_fraction`.

`SpotOrderBookDetail` is the same minus every perp-only field (no margin fractions, no `open_interest`,
no `market_config`, no funding fields). `OrderBookDetails` returns both arrays side by side:
`{ code, order_book_details: PerpsOrderBookDetail[], spot_order_book_details: SpotOrderBookDetail[] }`.

`MarketConfig`:
```
market_margin_mode i32 · insurance_fund_account_index i64 (sentinel 281474976710655 = 2^48-1 = "none")
liquidation_mode i32 · force_reduce_only bool · funding_fee_discounts_enabled bool?
trading_hours string ("" = 24/7; non-empty for RWA/equity markets)
hidden bool · rfq_enabled bool
```

### 10.4 Order book depth — `OrderBookOrders`, `SimpleOrder`

`GET /api/v1/orderBookOrders?market_id&limit` (limit `1..250`) returns **individual resting orders**, not
aggregated price levels:

```
{ code, total_asks: i64, asks: SimpleOrder[], total_bids: i64, bids: SimpleOrder[] }

SimpleOrder = {
  order_index          i64     562952978777307
  order_id             string  "562952978777307"   ← canonical
  owner_account_index  i64
  initial_base_amount  string  "0.04220"
  remaining_base_amount string "0.00220"
  price                string  "64365.6"
  order_expiry         i64     epoch ms
  transaction_time     i64     epoch µs (often 0 here)
}
```

`asks` ascend by price, `bids` descend (verified). `total_asks`/`total_bids` are the **returned** counts,
not book totals — do not use them for depth statistics.

Aggregated price-level depth (`PriceLevel {price, size}` / `OrderBookDepth`) is **WebSocket-only**; there
is no REST equivalent. Anyone needing an aggregated book must either subscribe or fold `SimpleOrder[]`
themselves.

### 10.5 Orders — `Order`, `Orders`

From `GET /api/v1/accountActiveOrders` and `GET /api/v1/accountInactiveOrders` (both auth-required).


Two things to preserve exactly:

- The 17-member `status` union and the `to_trigger_*`/`to_cancel_*`/`parent_order_*` fields encode the

### 10.6 Candles — `Candle`, `Candles`

`GET /api/v1/candles`. Deliberately abbreviated single-letter keys, **case-sensitive**, at most 500
candles per call:

```
t  i64   open time, epoch ms   (end time if set_timestamp_to_end=true)
o  f64   open           h  f64  high          l  f64  low          c  f64  close
v  f64   base volume    V  f64  quote volume  (LOWERCASE v ≠ UPPERCASE V)
i  i64   interval/index
C  f64?  H f64?  L f64?  O f64?   — secondary/index OHLC series, ABSENT when zero
```

`Candles = { code, r: string /* resolution echo */, c: Candle[], message? }` — note the response array is
also called `c`, colliding with the per-candle close field one level down. Verified live: `C/H/L/O` are
absent on BTC.

Resolutions: `candles` accepts `1m|5m|15m|30m|1h|4h|12h|1d|1w`; `pnl` accepts a *different, smaller* set
`1m|5m|15m|1h|4h|1d` (no `30m`, `12h`, `1w`); `fundings` accepts only `1h|1d`. Do not share one enum
across the three — three distinct unions.

`start_timestamp`/`end_timestamp` are epoch **ms**, range-checked `0 .. 5_000_000_000_000`. Over-wide
windows fail with code `22403`. **The SDK should map single-letter keys to readable names**
(`{ time, open, high, low, close, baseVolume, quoteVolume }`) at the edge — this is the one place where
faithfulness to the wire actively harms ergonomics, and the mapping is lossless and mechanical.

## 11. Recommended TypeScript design

### 11.1 The decision: hand-authored route table + generated long-tail types

**Do not run an OpenAPI generator as the build's source of truth.**

The reasoning is not aesthetic. Section 9 establishes that the only available OpenAPI document is wrong in
a way that matters — it marks fields required that the server omits, and omits fields (`mark_price`,
`index_price`) the server sends. A generator faithfully reproduces both errors. And there is **no live
spec endpoint to regenerate from**: `/swagger/doc.json`, `/api/v1/swagger/doc.json`, `/swagger.json`,
`/docs/doc.json`, and `/openapi.json` all return `403` from the CDN. The only copy of the document is a
snapshot vendored into a third-party SDK repo, with `info.version = ""` — unversioned, so drift is
undetectable. Building the type layer on that is building on sand.

The shape that is actually correct:

```
src/
  transport.ts     ~150 LOC   fetch wrapper: URL build, auth inject, timeout, retry, error mapping
  routes.ts        ~400 LOC   one const object: 78 route descriptors, fully typed
  models/core.ts   ~600 LOC   the ~40 trading models, hand-authored, correct optionality
  models/generated.ts         the ~100 long-tail models, generated, all-optional
  client.ts        ~200 LOC   thin namespaced facade over routes
  paginate.ts       ~60 LOC
  errors.ts         ~80 LOC
  profiles.ts       ~30 LOC
```

Under 1600 lines of hand-written code for the whole REST surface — smaller than the ~15k LOC the Python
generator emits, and correct where the generator is not.

### 11.2 Route definitions

One declarative table, no per-endpoint functions:

```ts
export const routes = {
  orderBooks: {
    method: 'GET', path: '/api/v1/orderBooks', auth: 'none',
    query: {} as { market_id?: number; filter?: 'all' | 'spot' | 'perp' },
    response: {} as OrderBooks,
  },
  accountActiveOrders: {
    method: 'GET', path: '/api/v1/accountActiveOrders', auth: 'required',
    query: {} as { account_index: number; market_id?: number; market_type?: MarketType },
    response: {} as Orders,
  },
  sendTx: {
    method: 'POST', path: '/api/v1/sendTx', auth: 'none', encoding: 'form',
    body: {} as ReqSendTx,
    response: {} as RespSendTx,
  },
} as const satisfies Record<string, RouteDef>
```

The `{} as T` phantom-property idiom carries types with **zero runtime cost** — the object literal is
empty and the property is erased. Combined with `as const satisfies`, this gives exhaustive checking of
the table against `RouteDef` while preserving literal key types for the facade.

This yields:
- Full inference on both input and output from one declaration site.
- A single `request()` implementation — no 78 near-identical functions.
- Tree-shaking: `routes` is a plain object literal of plain data. A bundler with
  `"sideEffects": false` drops unreferenced entries. If measured tree-shaking proves insufficient,
  the fallback is one module per group (`routes/order.ts`, `routes/account.ts`, …) re-exported from a
  barrel, which guarantees group-level granularity.
- Auth requirement is **data on the route**, which is exactly what §5.4 requires (it cannot be derived).

### 11.3 Transport

```ts
export interface LighterConfig {
  profile?: EndpointProfile | keyof typeof profiles   // default: mainnet
  baseUrl?: string                                    // overrides profile.restBase
  auth?: string | AuthProvider
  fetch?: typeof globalThis.fetch                     // injection point for tests, proxies, Workers
  timeoutMs?: number                                  // default 10_000
  retry?: { attempts?: number; baseMs?: number; capMs?: number }
}
```

Request pipeline: resolve route → build `URL` + `URLSearchParams` (omit `undefined`, lowercase booleans,
repeat array keys for the two `multi` params) → resolve auth if `route.auth !== 'none'` → set
`Authorization` → encode body per `route.encoding` → `AbortSignal.any([timeout, userSignal])` → `fetch` →
classify.

Classification, in order:
1. `!res.ok` and body is not JSON → `LighterBlockedError` (the CloudFront HTML case).
2. `!res.ok` and body is JSON → `LighterApiError`, or `LighterAuthError` when status is 401 or code 20013.
3. `res.ok` and `body.code` present and `!== 200` → `LighterApiError` (defence in depth; not observed).
4. Otherwise → typed body.

Everything used here — `fetch`, `URL`, `URLSearchParams`, `AbortSignal.timeout`, `AbortSignal.any` — is
present on Bun 1.3, Node 20+, Deno, Workers, and modern browsers. **Zero runtime dependencies.**
`AbortSignal.any` is the only member worth verifying on the oldest supported Node 20 patch; a six-line
manual fallback removes the risk entirely.

### 11.4 The facade

Group namespaces preserve the familiar shape without 13 classes:

```ts
const client = new LighterClient({ profile: 'mainnet', auth: signer.authProvider })
const books  = await client.order.orderBooks({ filter: 'perp' })
const orders = await client.order.accountActiveOrders({ account_index: 42 })
```

Built by mapping over `routes` grouped by tag. Also export the bare `request(route, params, config)` so
advanced users and tree-shaking-sensitive bundles can skip the facade object entirely.

**Parameter naming:** keep wire `snake_case` in the public API. Camel-casing is superficially nicer but
forces a bidirectional mapping layer over 142 models, breaks the ability to paste a field name from the
API docs into code, and creates a permanent drift surface. One convention, applied everywhere, documented
once. The one exception is candles (§10.6), where the wire keys are single letters and a mapping is
genuinely clarifying.

### 11.5 Generating the long tail

Generate `models/generated.ts` in a **checked-in, manually-run** step — not a build step, because the
input document is a static vendored snapshot with no upstream to poll.

```
bun run scripts/generate-models.ts   # reads spec/openapi.snapshot.json → src/models/generated.ts
```

Requirements on the generator:
1. **Force every response field optional.** Ignore `required` entirely (§9.2). This is the whole reason a
   stock generator will not do.
2. Emit interfaces + literal unions only. No classes, no runtime validators, no decorators — the output
   must fully erase.
3. Skip anything hand-authored in `models/core.ts`; the file re-exports from core so consumers see one
   namespace.
4. Normalise the `uin16` typo to `number`.
5. Emit `// @generated` and a hash of the source document so drift is visible in review.

Write it as a ~200-line script over the JSON. Pulling in `openapi-typescript` adds a devDependency and a
plugin config to work around defects it was not built to work around; a bespoke script is smaller and does
exactly what is needed. Vendor the document as `spec/openapi.snapshot.json` with a README noting it is a
snapshot of unknown vintage that the live API contradicts.

### 11.6 Runtime validation

**Do not validate response bodies by default.** No Zod, no ArkType. Reasons: it would add a runtime
dependency (violating the constraint), it would cost real time on hot paths, and — decisively — the schema
we would validate against is known-wrong, so it would reject valid live responses (§9.2).

Instead: types are compile-time only; the transport validates the **envelope** (status, `code`, JSON
parseability) and nothing more. Offer an optional `onResponse` hook so a user who wants schema checks can
add their own.

### 11.7 Pagination helper

```ts
export async function* paginate<R extends PaginatedRoute>(
  client: LighterClient, route: R, params: ParamsOf<R>, opts?: { maxPages?: number },
): AsyncGenerator<ResponseOf<R>>
```

Reads `next_cursor ?? cursor` (§6), stops when both are absent, throws on a repeated cursor, and respects
`maxPages` (default 1000). Plus `paginateItems()` that flattens using a per-route `itemsKey`.

### 11.8 Package shape

- ESM only. No CJS build — every target runtime supports ESM, and dual-publishing creates dual-package
  hazards for no gain here.
- `"type": "module"`, `"sideEffects": false`.
- Explicit `exports` map with subpath entries so a consumer can import only what they need:
  `.`, `./rest`, `./models`, `./errors`, `./profiles` (and, from sibling specs, `./signer`, `./ws`).
- `"engines": { "node": ">=20" }`. Ship `.d.ts` alongside `.js`; no `.d.ts` bundling.
- `tsconfig`: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`,
  `verbatimModuleSyntax`, `moduleResolution: "bundler"`, `target: "es2022"`.
- **Zero `dependencies`.** Verified achievable: nothing in this spec needs a library.

### 11.9 Ergonomic fixes over the reference SDKs

Places where the references are bad and the TS version should deliberately differ:

| Reference behaviour | Replacement |
|---|---|
| 300 s default timeout | 10 s read / 30 s write |
| Exponential retry with `factor=0.0` (a spin loop) | Jittered backoff, capped, GET-only |
| `code`-first success check (breaks on the 3 envelope-less endpoints) | HTTP-status-first (§3.2) |
| 13 API classes each requiring an `ApiClient` | one client, grouped namespaces |
| 3 method variants per operation (`x`, `x_with_http_info`, `x_without_preload_content`) — 234 methods | one method; `{ raw: true }` option returns the `Response` |
| `auth` threaded manually through call sites | injected by the transport from an `AuthProvider` |
| Two cursor field names leaking to callers | one normaliser |
| Dead exception classes (`NotFoundException` can never fire) | 5 real error classes (§4.3) |
| Native `.so` loaded via `ctypes` for signing | pure TS (sibling spec) |
| `nonce` fetched with a **blocking** `requests.get` inside an async client | async-only, cached, invalidated on 401 |
| `Configuration` object with ~30 unused fields (proxies, TLS client certs, cookies, basic auth) | ~6-field config; `fetch` injection covers all of it |

### 11.10 Testing

- **Golden-response fixtures.** Capture real responses from mainnet for the ~40 core models, check them
  in, and assert the hand-authored types accept them (`satisfies`) with no excess-property errors. This is
  the only test that would have caught the §9.2 drift, and it must run in CI.
- **Query-serialisation table tests** — booleans, omitted values, the two repeated-array params,
  percent-encoding of the `auth` token's colons.
- **Error-mapping tests** from captured bodies, including the CloudFront HTML 403.
- **Live smoke test**, opt-in via env var, hitting every public GET on testnet and asserting only that the
  envelope parses. Not in the default CI path — it would make CI depend on a third-party uptime.
- **Runtime matrix in CI:** Bun, Node 20, Node 22, Deno, and `workerd` via Wrangler. The point is to catch
  a `AbortSignal.any`-class API gap, so it must actually execute requests against a local mock server.

## 12. Risks

1. **The vendored OpenAPI document is the only machine-readable source, it is unversioned, it is
   demonstrably wrong, and there is no live endpoint to refresh it from.** Every generated type inherits
   that. Mitigated by golden fixtures, not by better generation.
2. **`omitempty` optionality is a moving target.** A field that is non-zero today and typed non-optional
   becomes `undefined` the moment the server's data changes. The all-fields-optional rule is the only safe
   posture, and it costs ergonomics on every access.
3. **Undocumented, open-ended error codes.** Modelled as `number` + constants; a `switch` on codes cannot
   be exhaustive.
4. **CDN interposition is IP-dependent.** Endpoints that 403 from CI may work from a user's machine and
   vice versa. Live tests will be flaky; keep them out of required CI.
5. **`int64` above 2^53.** Order/trade id sequences are monotonic. The `_str` convention covers today's
   fields, but a future `int64` field without a `_str` twin will silently corrupt.
6. **Auth semantics diverge from the document** on at least six endpoints. The corrections in §5.4 are
   from point-in-time probing and could themselves drift.
7. **Rate limits are unpublished and undetectable** until they fire. `volume_quota_remaining` on
   `sendTx` is the only signal.
8. **Robinhood profiles are unverified.** They appear in the reference profile table but were not probed;
   they may require different auth or expose a different subset of endpoints.

## 13. Open questions

1. **How is a Scheme-B managed `api_token` transmitted?** Nothing in either SDK, the OpenAPI document, or
   the examples consumes the value returned by `tokens/create`. Presumed `Authorization`, unverified.
   → Resolve by minting one against testnet and probing.
2. **What is the `scopes` grammar?** Observed default `read.*`. Is it glob, prefix, or a fixed set? What
   scopes exist beyond read?
3. **What does `market_flags` (i32 bitfield, live-only) encode?** It is absent from the document entirely.
4. **What are `multiplier` and `quote_multiplier` on markets, and `multiplier` on assets?** Live-only,
   observed `"1.000000000000000000"` and `1`. They look like they participate in size/price scaling, which
   would make them load-bearing for order submission — but the reference signers use only
   `supported_size_decimals`/`supported_price_decimals`. Must be resolved before shipping order helpers.
5. **Are `blocks` / `currentHeight` / `accountTxs` genuinely available?** They 403'd from a datacenter IP.
   Need a probe from a residential IP to distinguish WAF policy from a decommissioned endpoint.
6. **Do the Robinhood profiles expose the same 78 operations?**
7. **Is `price_protection` on `sendTx` a slippage guard, and what is its default?** Undocumented.
8. **Is there a published rate-limit policy?** And does the API ever emit `429` with `Retry-After`, or does
   the CDN always absorb it as a 403?
9. **`sort_dir` on `trades` has exactly one legal value (`desc`).** Is ascending genuinely impossible, or
   is the enum under-specified?
10. **Which endpoints are safe to cache, and for how long?** No `Cache-Control` was returned on any probed
    response; `X-Cache: Miss from cloudfront` implies caching is configured but the policy is invisible.
